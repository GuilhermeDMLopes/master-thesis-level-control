# Gateway OPC UA Command and Feedback Interface

## Document Purpose

This document defines the command and feedback interface between the Python OPC UA gateway and 4diac FORTE.

The interface is defined before implementation to avoid introducing ambiguous command sources or breaking the existing 4diac application.

No gateway behavior is changed by this document.

## Current Interface

The current gateway OPC UA server exposes the following NodeIds:

| NodeId | OPC UA Type | FORTE Access | Meaning |
|---|---|---|---|
| `Nivel` | `Double` | Read | Raw level feedback from the B&R PLC |
| `Enable` | `Boolean` | Read and write | Enable command generated by FORTE |
| `DAC` | `Int16` | Read and write | DAC command generated by FORTE |

The current gateway reads the actual Enable and DAC values from the B&R PLC for CSV logging.

However, these PLC feedback values are not exposed as separate OPC UA NodeIds to FORTE.

## Current Ambiguity

The current NodeIds `Enable` and `DAC` represent commands.

They do not represent independent confirmation that the B&R PLC received or applied those values.

The gateway stores:

```text
last_enable_command
last_dac_command
```

These variables contain the last commands forwarded by the gateway.

They must not be interpreted as PLC feedback or command acknowledgement.

## Proposed Backward-Compatible Interface

The existing NodeIds will be preserved:

| NodeId | OPC UA Type | Access | Role |
|---|---|---|---|
| `Nivel` | `Double` | Read only | Process feedback |
| `Enable` | `Boolean` | Read and write | Legacy Enable command |
| `DAC` | `Int16` | Read and write | Legacy DAC command |

The following feedback NodeIds will be added:

| NodeId | OPC UA Type | Access | Role |
|---|---|---|---|
| `EnableFeedback` | `Boolean` | Read only | Actual Enable value read from the B&R PLC |
| `DACFeedback` | `Int16` | Read only | Actual DAC value read from the B&R PLC |

The complete interface will therefore be:

```text
Nivel
Enable
EnableFeedback
DAC
DACFeedback
```

## Command Source of Truth

During this migration, the only command NodeIds will remain:

```text
Enable
DAC
```

The gateway must not introduce a second writable command interface during the same stage.

NodeIds such as:

```text
EnableCommand
DACCommand
```

will not be created yet.

Creating both legacy and new writable command NodeIds would require a command arbitration policy.

That arbitration policy is outside the scope of the current structural refactoring.

## Feedback Source of Truth

The feedback NodeIds will always originate from values read directly from the B&R PLC:

```text
EnableFeedback <- B&R Enable
DACFeedback    <- B&R DAC
```

They must not be populated from:

```text
last_enable_command
last_dac_command
Enable
DAC
```

The command value and the feedback value may temporarily be different.

That difference is important for communication diagnostics.

## OPC UA Access Rules

### `Nivel`

- Gateway writable.
- FORTE read only.
- Updated from the B&R level value.

### `Enable`

- FORTE writable.
- Gateway readable.
- Used as the command sent to the B&R PLC.

### `EnableFeedback`

- Gateway writable internally.
- FORTE read only.
- Updated from the actual B&R Enable value.
- Must not be marked writable through the OPC UA server.

### `DAC`

- FORTE writable.
- Gateway readable.
- Used as the command sent to the B&R PLC.

### `DACFeedback`

- Gateway writable internally.
- FORTE read only.
- Updated from the actual B&R DAC value.
- Must not be marked writable through the OPC UA server.

## OPC UA Data Types

The initial implementation must preserve the existing OPC UA types:

```text
Nivel           -> Double
Enable          -> Boolean
EnableFeedback  -> Boolean
DAC             -> Int16
DACFeedback     -> Int16
```

The B&R DAC value and the gateway DAC values must remain inside the valid `Int16` range.

The configured operational DAC range remains:

```text
0 to 32000
```

## Initial Values

When the gateway starts, it already reads:

```text
initial_raw_level
initial_enable
initial_dac
```

The new feedback NodeIds must be initialized with:

```text
EnableFeedback = initial_enable
DACFeedback    = initial_dac
```

This prevents the feedback variables from starting with arbitrary default values.

## Update Strategy

The current gateway already reads confirmation values from the B&R PLC during CSV logging:

```text
confirmed_enable
confirmed_dac
```

The first implementation will reuse these existing values to update:

```text
EnableFeedback
DACFeedback
```

This avoids adding additional PLC reads during the initial interface change.

The feedback update sequence will be:

```text
Read B&R feedback
    |
    +-> Update EnableFeedback
    |
    +-> Update DACFeedback
    |
    +-> Write values to CSV
```

The current values are read at the configured logging period:

```text
LOG_PERIOD_S = 0.1
```

The feedback polling period may be separated from the CSV logging period in a later timing and diagnostics stage.

## Communication Failure Behavior

If a B&R feedback read fails:

1. The gateway must log the exception.
2. The current cycle must not publish an artificial zero value.
3. The feedback NodeIds must retain the last successfully read values.
4. The gateway loop may continue according to the existing error-handling behavior.

Explicit connection-state NodeIds will be introduced in a later stage.

Possible future diagnostics include:

```text
BRConnected
GatewayReady
FeedbackValid
LastError
LastSuccessfulRead
```

These diagnostics are outside the current interface implementation.

## Command and Feedback Comparison

The new interface will allow FORTE and CSV analysis to compare:

```text
Enable == EnableFeedback
DAC == DACFeedback
```

A difference does not automatically indicate an error.

Temporary differences may occur because of:

- Communication delay.
- PLC scan timing.
- Actuator limiting.
- PLC safety logic.
- Gateway cycle timing.
- Value conversion.
- Failed or delayed writes.

The interface only exposes the values. Fault-detection rules will be defined later.

## Compatibility Requirements

The implementation must preserve:

- The existing `Nivel` NodeId.
- The existing `Enable` NodeId.
- The existing `DAC` NodeId.
- Existing OPC UA data types.
- Existing B&R NodeIds.
- Existing CSV columns.
- Existing gateway endpoint.
- Existing namespace URI.
- Existing 4diac application behavior.

The current 4diac project must continue to operate without modification after the feedback NodeIds are added.

## 4diac Migration Strategy

The initial gateway implementation will not require changes in 4diac.

The current application may continue using:

```text
Nivel
Enable
DAC
```

After the gateway implementation is validated, new OPC UA read blocks may be added to 4diac for:

```text
EnableFeedback
DACFeedback
```

Those blocks will be used for diagnostics and experimental logging.

They must not initially affect the PI controller output.

## Planned Implementation Sequence

The implementation will follow this order:

1. Add constants for the new NodeId names.
2. Create `EnableFeedback` during gateway server startup.
3. Create `DACFeedback` during gateway server startup.
4. Initialize the variables with the first B&R values.
5. Keep both feedback variables read only for FORTE.
6. Update them with actual B&R feedback values.
7. Preserve the existing command NodeIds.
8. Preserve the existing CSV structure.
9. Add offline tests for feedback synchronization logic.
10. Validate that the current 4diac project still opens and runs without changes.

## Out of Scope

The following changes will not be performed in the initial command and feedback separation:

- Renaming `Enable` to `EnableCommand`.
- Renaming `DAC` to `DACCommand`.
- Removing legacy NodeIds.
- Adding command arbitration.
- Adding a second writable command interface.
- Modifying the PI controller.
- Modifying the MPC.
- Changing the PLC application.
- Adding automatic fault detection.
- Adding an explicit reconnection state machine.
- Changing the CSV columns.
- Changing communication periods.

## Acceptance Criteria

The interface implementation will be accepted when:

- Existing 4diac NodeIds continue to work.
- `EnableFeedback` is available as a read-only Boolean.
- `DACFeedback` is available as a read-only Int16.
- Feedback variables are initialized from the B&R PLC.
- Feedback variables are updated from actual B&R values.
- Feedback variables are not copied from gateway command values.
- Existing tests continue to pass.
- New offline tests pass.
- No PLC connection is required for the unit tests.
- The gateway source passes syntax validation.
- The 4diac project remains compatible.
